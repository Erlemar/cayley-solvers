# T1.1 — Curated speedcubing macros: refined strategy

Drafted 2026-05-02 after initial scoping research. Updates the merged tier
doc's T1.1 entry with practical implementation notes.

## Reframe: it's NOT raw algorithm-string scraping

Initial mental model: scrape ~100 speedcubing algorithm strings → translate
to our notation → plug in. **This is wrong** for two reasons:

1. Speedcubing notation is **last-layer-only** (U, R, F, L, D). The wiki
   confirms: "EOLL: 3 algorithms, OCLL: 16, EPLL: 5, CPLL: 15, PLL: 151,
   OLL: 259, ELL: 39 — total 411 in 2LLL". All of these operate on the top
   layer; our solver uses ALL 12 faces (24 generators with inverses).

2. The same physical permutation has DIFFERENT shortest representations
   depending on which generators you have available. A "U-perm" (3-cycle
   of last-layer edges) has one canonical algorithm string in 3×3 notation;
   in our 24-gen system it might be a totally different 4-6 move sequence.

## Refined strategy: useful-permutation mining

The actually-useful objects are **permutations** (not algorithm strings).
Speedcubing has identified, over decades, the permutations that are
"useful" — the 3-cycles, swaps, orientations that show up repeatedly in
real solves. The macro library should be:

1. **A curated list of useful named permutations** (~30-100 total):
   - 3-cycle of corners (4 distinct chiralities)
   - 3-cycle of edges (4 distinct chiralities)
   - Edge swaps (U-perm, H-perm, Z-perm analogs)
   - Corner swaps (A-perm, J-perm, T-perm analogs)
   - 4-cycle and 2+2 cycle PLLs
   - OLL orientations as permutations
   - Useful commutator atoms from the FMC community

2. **For each, look up the shortest representation in our 24-generator
   system**:
   - Most useful permutations are at d=8..14 from solved
   - Our `data/bfs_bytes_d6.pkl` has 19.4M perms at d≤6 — too small for
     useful macros (a 3-cycle isn't a d≤6 perm typically)
   - Need either: BFS-d8+ (250M states, infeasible on local), MITM
     between BFS-d6 from solved and BFS-d6 from each target perm
     (feasible: per-target ~4 GB RAM at peak, ~10 sec compute), or
     a direct beam search to each target perm (slower but bounded)

3. **Plug into MacroInsert in T1.6**: the macro library becomes the
   insertion candidate set. T1.6 already empirically validated MacroInsert
   with brute-force d=4 commutators (7.8% accept rate); curated macros
   should be 3-10× higher quality.

500 redundant ones.

## Implementation plan (engineering)

```
megaminx/scripts/31_build_macro_library.py
```

1. Parse a curated YAML file `megaminx/data/named_permutations.yaml` with
   entries like:
   ```yaml
   - name: "3-cycle UFR-UFL-UBR (corners)"
     description: "A-perm a equivalent for last layer corners"
     # Define the permutation by piece-position swaps:
     swaps:
       - [piece_idx_1, piece_idx_2, piece_idx_3]  # 3-cycle
   - name: "U-perm (edge 3-cycle)"
     swaps: [...]
   ```
2. For each named perm, compute the resulting megaminx state.
3. Find the shortest word producing that perm in our 24 generators:
   - Try BFS-d6 lookup first (free, fast)
   - If not in d≤6 shell, run a SHORT beam search from solved with target
     state being the perm applied to solved (~10s/perm at beam 16k)
   - Fallback: use the speedcuber's own algorithm translated via our
     notation map, if a clean translation exists
4. Save as `megaminx/data/named_macros.pkl`:
   ```python
   {"name_to_word": {"3-cycle UFR-UFL-UBR": [3, 7, 12, ...], ...}}
   ```
5. Modify `27_path_sa.py` to load this file as `macros` (plug into
   existing MacroInsert).

## Notation translation

For algorithms specified in speedcuber notation (R U R' U' etc.),
the 5 last-layer faces map to a SUBSET of our 12 faces:

| Speedcuber | Our generator | Notes |
|---|---|---|
| U | U | top face, same |
| R | one of {DR, FR, BR} | depends on orientation; need to fix a convention |
| L | one of {DL, FL, BL} | same issue |
| F | F | front face |
| B | B | back face |
| D | D | bottom face (only used for `D'` setups in last-layer algs) |

The R/L ambiguity is the real complexity — speedcubing uses the
"current orientation" of the puzzle, which we'd need to fix. The
cleanest approach: always interpret "R" as our `DR` generator (the
right-front-down face), `L` as `DL`, etc., and validate empirically by
applying the algorithm to a solved cube and checking the resulting
permutation matches the documented expected effect.

## Acceptance criterion

A macro is valuable iff:
- The permutation it produces is NEW (not reachable in d≤2 on its own —
  d≤2 perms are already trivially explored by beam)
- Its shortest representation in our 24 generators is ≤ 12 moves (longer
  macros are too expensive to insert)
- It targets piece structures common in beam-search residues (3-cycles,
  swaps, orientations of small piece sets)

the brute-force commutators were the issue and we need a different
approach.

## Open questions

1. **Megaminx vs 3×3×3 piece geometry**: A "3-cycle of UF-UR-UL edges"
   on 3×3 is a specific permutation. The same NAMED 3-cycle on megaminx
   involves different physical pieces. Need a megaminx-specific source
   (Odder's guide, megaminx PLL PDF) not just 3×3 PLL.

2. **Notation translation R/L ambiguity**: Need to verify by running
   each candidate algorithm against the documented expected effect.
   This is per-algorithm validation, not bulk translation.

3. **Permutation discovery vs algorithm string**: Once we have the
   PERMUTATION (regardless of how we got it), we can find OUR shortest
   word for it independently of the original algorithm string. This is
   the key insight — we don't translate algorithms, we extract their
   end-state and re-derive the path.
