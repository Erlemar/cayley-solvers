# Two-phase (Kociemba-style) megaminx solver — experiments

Concise index of the two-phase solver work (method from the "CayleyPy Growth BFS"
chat, 2026-06-15; built 2026-06-16/17). Full design + handoff: [two_phase_plan.md](two_phase_plan.md).

**Idea.** Split the solve into two stages (à la Kociemba): **Phase 1** reduces an
arbitrary scramble into the subgroup `H` generated by 6 of the 12 faces (a `MaskedV`
treats the 85 stickers those faces can move as don't-care, target = the 35 "frozen"
stickers home); **Phase 2** finishes inside `H` using only those 12 generators. Each
stage is an easier search, so at a fixed beam width the total path is much shorter than
single-stage — at the cost of optimality (it blocks some optimal paths).

## Experiments

1. **Implementation + unit tests.** Decomposition: 35 frozen (== LL) / 85 movable;
   TOP moves provably never disturb the frozen stickers; mask-by-value preserves the
   frozen-sticker placement. `MaskedV` + `torch.compile` OK. `tests/test_two_phase.py` 6/6.

2. **Training (pretrain).** `m_phase1_v0` (1500 ep, full 24-gen, masked) + `m_phase2_v0`
   (2000 ep, restricted 12-gen), 6.05M each, local 4090, fast recipe.

3. **Local two-stage solve + beam sweep** ([112](scripts/112_two_stage_solve.py)).
   Reproduces the chat's curve on an 11-pid spread: **80.9 @ 2¹⁶ → 79.6 @ 2¹⁷**, split
   ~27 (Phase 1) + ~53 (Phase 2), **11/11 solved**; the single-stage baseline (`m_dd_v0`,
   single-pass) **failed 4/6** at 2¹⁶ where two-stage solved all. **vs the 73,441 floor
   (mean 73.4, merged+rescued): marginal** — beats the floor only on the ~2/11 spread pids
   left at 80 (un-rescued); the 240 floor≥80 pids are the realistic rescue target.

4. **V0-calibration refine** ([114](scripts/114_refine_phase2.py)). `m_phase2_v0` never
   saw depth-0 (walks emit depths 1..k), so `V(solved)=4.47` (solved not the V-minimum) —
   a real, latent bug. V0/depth-1 anchors → **`m_phase2_v1`, `V(solved)=0.03`**, clean
   monotonic landscape, still solves locally. Follow-up implementation now folds the
   same anchor family into `110` by default.

5. **Hybrid TPU port** (the chat-requested "session model @64M on TPU", pid 993). Phase 1
   barely scales with beam, so run it local @2¹⁷ ([113](scripts/113_phase1_export.py) →
   27 moves, H-state in `H`); run Phase 2 @64M on zakhar's v4-8 (restricted 12-gen,
   `m_phase2_v1`, phase2 TPU driver). **Result: 27 + 50 = pid 993 = 77, verified**
   (floor 69, +8). Two-phase's hard-tail ceiling is ~77; it does not beat the community
   floor there (that took 48M-beam × 20+ rotations). Value was the at-scale validation.

## Findings (reusable)

- **`V(solved)` calibration is a real model-quality issue** for any V trained on
  walk-depth (depth-0 is never sampled). Latent locally; fix with V0/d1 anchors (see 114).
  `110_train_phase2.py` now mixes solved/d1 anchors from the start.
- **Phase-1 needs true coset signal.** Generic full-walk labels make TOP-only H states
  inherit positive walk depths even though their Phase-1 distance-to-H is 0.
  `111_train_phase1.py` now mixes restricted-H zero-label anchors every epoch.
- **TPU `test.csv` must quote the comma-separated state** (`0,"v0,v1,..."`). Unquoted →
  `csv.DictReader` keeps only the first value → length-1 state → JAX OOB-clamp → silent
  degenerate beam that never solves. Cost a multi-hour phantom-"kernel-bug" hunt; the
  restricted-12-gen kernel was fine all along. `115_prepare_phase2_tpu_inputs.py` writes
  the quoted CSV and `gcp_beam_v_only.py` now refuses wrongly parsed state lengths.

## Verdict

Method validated end-to-end (local + at TPU scale); reproduces the chat's `<80 @ 2¹⁷`.
Hard-tail pids won't beat the community floor even at 64M — the two-phase leverage is the
**mid-difficulty bulk** via min-merge (a local/GCP full-1001 job), not hard-tail TPU rescue.
